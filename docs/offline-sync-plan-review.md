# Валидация плана offline-sync

Ревью плана [`offline-sync-plan.md`](./offline-sync-plan.md) против реального кода
(схема, репозитории, server actions, формы, DAL, auth, dates, summary).

## Вердикт

Архитектура в целом **здравая и адекватна масштабу** (один юзер, 2–3 девайса,
низкая конкуренция). Outbox + delta-pull + sync-time LWW — стандартный и разумный
выбор; CRDT тут оверкилл, отказ от него правильный. Большинство точечных решений
совпадают с реальностью кода. Но есть несколько конкретных пробелов, не закрытых
планом, — по убыванию серьёзности.

## Что подтверждается кодом (solid)

- **Клиентские UUID.** `id: uuid().primaryKey().defaultRandom()` у
  `expenses`/`categories`, `user.id` тоже `uuid` (`auth.ts` +
  `advanced.database.generateId: "uuid"`). Postgres-`uuid` принимает
  `crypto.randomUUID()` в upsert.
- **`updatedAt`/`deletedAt` + backfill + индекс `(user_id, updated_at, id)`** —
  ложится на Drizzle-миграцию чисто; `migrate.ts` гоняет папку миграций на старте
  контейнера.
- **Изоляция по `userId`** уже всюду (`and(eq(userId...))`), sync-эндпоинты за
  `requireSession` — паттерн уже есть в actions.
- **Клиентский `userId` для имени БД `moneta-${userId}`** — доступен через
  `authClient.useSession()` (`auth-client.ts`).
- **Переиспользование zod на клиенте** — `ExpenseInput`/`CategoryInput`/
  `expenseFormSchema` уже DB-free и шарятся (`lib/categories.ts`,
  `lib/expense-form.ts`).
- **Серверный `updated_at = now()`** против кривых клиентских часов — правильный
  компромисс для личного трекера.

## Серьёзные пробелы (закрыть до Фазы A)

### 1. Уникальный индекс категорий несовместим с offline + soft-delete

`categories_user_name_uniq (userId, name)` (`schema/categories.ts:33`) план
игнорирует. Push-upsert описан как `ON CONFLICT (id)` — он **не ловит** конфликт по
имени, и три сценария дадут `23505`:

- Две девайса оффлайн создают «Еда» с разными `id` → пуш второго падает.
- **Soft-delete + пересоздание того же имени:** tombstone-строка остаётся и держит
  слот уникальности → новый insert падает. Типовой кейс, не экзотика.
- Оффлайн-переименование в уже существующее имя.

План §9 разбирает только «удаление непустой категории», про уникальность имени —
ни слова. Нужно: **partial unique index `WHERE deleted_at IS NULL`** (чтобы
tombstone не блокировал переиспользование) + **per-op обработка
`isUniqueViolation`** на push (хелпер `lib/db-errors.ts` уже есть) +
UX-реконсиляция на клиенте. Это меняет и миграцию (Фаза A), и контракт push.

### 2. Семантика soft-delete категории и FK `restrict`

Сейчас `categoryId` → `onDelete: "restrict"` (`schema/expenses.ts:42`), а
`deleteCategory` проактивно считает траты (`categories.ts:82`). При переходе на
soft-delete:

- FK-`restrict` больше **не срабатывает** (строка не удаляется) — защита «непустую
  нельзя» уезжает в app-логику, и счётчик трат должен стать
  **`deleted_at IS NULL`-aware** (иначе уже удалённые траты будут «держать»
  категорию).
- Нужно определить поведение **трат, ссылающихся на tombstone-категорию**:
  `summary` делает `innerJoin categories` (`expenses.ts:184`) — если категории
  фильтруются по `deleted_at`, такие траты молча выпадут из сводки и истории. Это
  семантический выбор, зафиксировать в плане.

### 3. Pull-курсор: одна сущность или две?

Внутренняя нестыковка плана. §3 `meta` хранит **один** `pullCursor {updatedAt,id}`,
а §2 описывает pull одним запросом по одной таблице. Но `expenses` и `categories` —
две таблицы с независимыми `(updated_at, id)`. Одним курсором их не покрыть. Нужно
либо **`?entity=expense|category` с отдельными курсорами**
(`meta.pullCursor.expenses` / `.categories`), либо единый change-feed. Поправить в
контракте (Фаза A).

### 4. Монотонность курсора при `updated_at = now()` (тихая дивергенция)

`now()` в Postgres = время **начала транзакции**. Перекрывающиеся push-транзакции
могут закоммититься в порядке, обратном их `now()`. Тогда pull, уже сдвинувший
курсор до `(t, id_big)`, **навсегда пропустит** строку, закоммиченную позже с
`(t, id_small)`. Это не конфликт (его решает LWW), а **молчаливая потеря строки на
pull**. Вероятность при 2–3 девайсах мала, но баг тихий. Митигиции: писать
`clock_timestamp()` в момент апдейта, перекрывать курсор небольшим окном при pull,
либо отдельный монотонный seq. В §12 это сейчас свёрнуто в «sync-time vs
edit-time», что не про эту проблему.

## Средние замечания

### 5. Объём refactor'а чтения занижен (§4)

План называет 3 файла (`page.tsx`, `history`, summary), но связки
`server-data → props → router.refresh()` шире: `quick-add-form` (локальный
`useState(categories)`), `edit-expense-dialog`, `use-expense-editor`,
`recent-list`, `history-list`, `period-tabs`, `category-select`,
`expense-form-fields` (инлайн-создание категории), `settings/category-manager`.
Все уйдут на Dexie/`useLiveQuery`. Плюс `lastUsedCategoryId` (сортировка по
`createdAt`, `expenses.ts:68`) надо пересчитывать на клиенте — значит **`createdAt`
обязан лежать в Dexie**. Перечислить в Фазе B/C явно.

### 6. Эхо собственных записей / churn updatedAt

Каждый push ставит `updated_at = now()`, поэтому девайс-автор перечитает свои же
записи на pull. Корректность спасают dirty-skip + `incoming.updatedAt >= local`,
но: после удаления op из outbox клиент должен **записать серверный `updatedAt` из
ответа push** в Dexie (план это возвращает — убедиться, что §6 `flush` его пишет),
иначе равенство по `>=` будет циклически переприменять. Рекомендую: на ack пишем
server `updatedAt`, дальше merge строгий `>`.

### 7. Партиал-фейл батча push

Не зафиксированы границы транзакций. Если весь батч в одной транзакции — отказ
одной op (напр. уникальность имени из п.1) откатит всё, и FK-порядок «категории
раньше трат» не спасёт. Нужно явно: **per-op (или per-entity) транзакции** +
определить поведение клиента на per-op error (оставить в outbox / дропнуть /
показать тост). Особенно для категории-дубля.

### 8. serwist + Next 16.2.6 + Turbopack (риск Фазы D)

План отмечает капризность в dev, но реальный риск — **build**: в Next 16 Turbopack —
дефолтный сборщик, а `@serwist/next` инжектит через webpack-хук. AGENTS.md прямо
предупреждает «это не тот Next, что вы знали». До Фазы D **проверить peer-deps
`@serwist/next` на совместимость с Next 16 / Turbopack-build**. Если не поддержит —
fallback на ручной Workbox/SW. Это feasibility-риск.

### 9. iOS PWA (телефон — основной таргет)

- **Background Sync API не поддерживается** в Safari/iOS — триггер `sync` из SW там
  не сработает. План спасают остальные триггеры
  (`online`/`visibilitychange`/after-mutation) — деградация ок, но **явно не
  зависеть** от `sync`-события.
- **Вытеснение IndexedDB через 7 дней** простоя на iOS; `navigator.storage.persist()`
  там слабый. Риск только для **несинхронизированного outbox при оффлайне >7 дней** —
  низкий, но упомянуть.

### 10. Логаут с непустым outbox

§8 говорит «удалить Dexie на логауте». Если в outbox есть несинхронизированные op —
это **тихая потеря данных**. Добавить: финальный `flush` перед удалением БД (онлайн)
либо предупреждение.

## Мелочи / на заметку

- **Дублирование `summary`** (§12): сервер сортирует `byCategory` по `sum desc` и
  берёт `::int` (`expenses.ts:181-192`); клиентская агрегация должна повторить
  порядок и целочисленность, и джойнить против Dexie-категорий с фильтром
  `deleted_at`. Рекомендую общий набор тест-векторов на оба пути.
- **Идемпотентность «естественная»** — верно для конечного состояния, но каждый
  реплей бьёт `updated_at` → лишний pull-эхо. `opId` серверу не нужен (план так и
  решил) — просто помнить про churn.
- **`output: "standalone"`** новым `/api/sync/*` не мешает; миграция-колонки
  подхватятся `migrate.ts`.

## По фазам

Зависимость **A → B → C → D, E сквозная** — правильная. Но Фаза A недоопределена:
до неё надо дорешить п.1 (partial unique index), п.2 (семантика soft-delete +
has_expenses), п.3 (один/два курсора), п.7 (границы транзакций push) — это и есть
«контракт», который A фиксирует для остальных. Иначе B/C/D будут переделываться.
